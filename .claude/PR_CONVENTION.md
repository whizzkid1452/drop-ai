# PR Convention

PR 생성 시 아래 규칙을 따른다.

## 원칙: PR은 항상 목적 단위로 나눈다

**서로 다른 변경 목적을 한 PR에 넣지 않는다.** 리뷰·머지·롤백·책임 범위가 PR 단위와 일치해야 한다.

- **권장이 아니라 규칙**이다. 도메인·검증 플랜·리스크가 갈라지면 **PR도 갈라진다**.
- **stacked PR**(베이스를 앞선 브랜치로 두는 연속 PR)을 활용해, 한 번에 “다 해결”하는 대신 **머지 가능한 조각**으로 나눈다.
- **커밋 분리**와 함께 본다. 커밋은 [COMMIT_CONVENTION.md](./COMMIT_CONVENTION.md)대로 항상 쪼개고, PR은 **그보다 한 단계 위**에서 “한 가치/한 목적”만 담도록 분리한다.
- **예외**는 팀이 정한 긴급 핫픽스·단일 라인 이슈 등 명시된 경우뿐이다. 기본은 나눈다.

## 1) 브랜치 네이밍

브랜치는 반드시 아래 prefix 중 하나로 시작해야 한다.

- `feature/`
- `bug/`
- `hotfix/`
- `refactor/`

허용 예시:

- `feature/thumbnail-ffmpeg-fallback`
- `bug/ruler-scroll-sync`
- `hotfix/export-crash-windows`
- `refactor/timeline-session-sync`

비허용 예시:

- `stack/pr1-ruler-sync`
- `chore/update-docs`
- `test/add-e2e`

## 2) PR 분리 원칙 (필수)

- 하나의 PR은 **하나의 변경 목적**만 포함한다.
- 기능 추가와 버그 수정은 같은 PR에 섞지 않는다.
- 대규모 변경은 **반드시** stacked PR로 나눈다.
    - 1차 PR: 기반 수정
    - 2차 PR: 인프라/리팩토링
    - 3차 PR: 전략/행동 변경

## 2.1) PR 쪼개기 기준 (언제 나눌지)

아래 중 **하나라도** 해당하면 분리를 우선 검토한다.

- **도메인·관심사**: 서로 다른 사용자 가치 축을 동시에 바꾸는 경우  
  예) 타임라인 스크롤·룰러 UI · 썸네일 파이프라인 · 미디어 디코딩/임포트 — 각각 별도 PR
- **리뷰·검증 단위**: 한 PR 설명·테스트 플랜으로 “무엇을 어떻게 확인했는지”가 두 갈래 이상으로 갈라지는 경우
- **의존성(스택)**: B가 A의 동작/타입/컨텍스트를 전제로 할 때, A를 먼저 머지할 수 있도록 **stacked PR**로 나눈다.
    - GitHub에서 뒤쪽 PR의 base를 앞선 브랜치로 두어 diff가 “그 단계만” 보이게 한다.
    - 머지 순서는 항상 스택의 **아래(베이스 쪽)에서 위로** 고정한다.
- **리스크 격리**: 회귀 범위가 넓은 리팩터링과 동작 변경(버그픽스·기능)을 한 PR에 넣지 않는다.
- **문서·포트폴리오 덩어리**: 제품 동작 변경과 무관한 장문 문서만 묶인 경우, 가능하면 **동작 변경 PR과 분리**한다. (동일 브랜치에 섞지 않음)

다음은 **“목적이 이미 하나인데”** 불필요하게 쪼개지 말라는 기준이다. (여러 목적을 한 PR에 넣는 것과는 별개다.)

- 파일 개수·라인 수만 보고 PR을 쪼개지 않는다. “한 가지 목적”이 여러 파일을 건드리는 것은 **한 PR**로 두어도 된다.
- 커밋 개수: 커밋은 목적별로 나누되, PR은 **그 목적이 하나면** 하나로 묶어도 된다.

**히스토리 정리**: 중간에 `revert` 후 `reapply`만 반복되는 구간이 있으면, 머지 전에 rebase로 정리하거나 PR 본문에 최종 net diff 기준으로 설명해 리뷰 비용을 줄인다.

## 3) PR 제목 형식

PR 제목은 커밋 컨벤션과 동일한 형식을 권장한다.

```text
<type>[optional scope]: <description>
```

예시:

- `fix(ruler): 타임라인 룰러와 플레이헤드 스크롤 동기화 수정`
- `refactor(thumbnail): 썸네일 생성 인프라와 세션 동기화 구조 정리`

## 4) PR 본문 템플릿

```md
## Summary

- 변경 목적 1
- 변경 목적 2

## Test plan

- [ ] 검증 항목 1
- [ ] 검증 항목 2
```

## 5) 금지 항목

- `feature|bug|hotfix|refactor` 외 prefix 사용
- **서로 다른 목적**·무관한 변경을 한 PR에 묶기 (PR 분리 규칙 위반)
- 검증 방법 없이 PR 생성
- PR 제목/본문/체크리스트/코멘트에 에이전트 이름, 도구명, 생성 서명 표기
    - 예: `Made with Cursor`, `Generated by Claude`, `Written by AI`
