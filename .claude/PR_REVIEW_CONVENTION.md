# PR Review Convention

PR 리뷰 시 아래 규칙을 따른다.

## 금지 조항

- 리뷰 코멘트에 에이전트 이름/도구명/생성 서명을 남기지 않는다
- 예: `Generated by Claude`, `Reviewed by AI` 금지

## 1) 리뷰 범위

- PR 설명(Summary, Test plan)을 먼저 읽고, 변경 목적을 파악한 뒤 리뷰한다
- 변경 목적과 무관한 코드는 리뷰 범위에 포함하지 않는다
- 포매팅 변경만 있는 부분은 로직 리뷰와 구분하여 별도로 언급한다

## 2) 코멘트 작성 원칙

### 톤

- **공손하고 협력적인 톤**을 유지한다
- 지시형("~하세요") 대신 제안형("~하면 좋을 것 같아요", "~는 어떨까요?")을 사용한다
- 좋은 부분은 먼저 언급하고, 개선점을 뒤에 남긴다
- 확신이 없는 부분은 "~일 수 있을 것 같아요", "제가 놓친 맥락이 있을 수 있는데" 등으로 표현한다

### 구조

- **본문 리뷰**: 전체 변경에 대한 총평을 먼저 남긴다
  - 잘 된 점, PR 범위/구조에 대한 피드백, 주요 우려사항 요약
- **인라인 코멘트**: 구체적인 코드 위치에 개선점을 남긴다
  - 무엇이 문제인지 → 왜 문제인지 → 어떻게 개선하면 좋을지 순서로 작성
  - 코드 예시가 있으면 함께 제시한다

### 분류

코멘트의 성격을 명확히 한다.

| 접두어 | 의미 | 예시 |
|--------|------|------|
| (없음) | 일반 의견/제안 | "유틸로 빼면 좋을 것 같아요" |
| `[nit]` | 사소한 스타일/네이밍 | "[nit] 변수명이 좀 모호한 것 같아요" |
| `[question]` | 이해를 위한 질문 | "[question] 이 분기는 어떤 케이스를 커버하는 건가요?" |
| `[bug]` | 버그 또는 잠재적 오류 | "[bug] timeout이 해제되지 않아 Promise가 풀리지 않을 수 있어요" |
| `[must]` | 머지 전 반드시 수정 필요 | "[must] 이 경로에서 사용자 데이터가 노출될 수 있어요" |

## 3) 리뷰 관점

아래 관점에서 순서대로 확인한다.

### 정확성

- 변경이 PR 설명의 목적을 달성하는가
- 엣지 케이스나 에러 경로를 놓치지 않았는가
- 기존 동작에 의도치 않은 변경(regression)이 없는가

### 안전성

- Promise 미해제, 타임아웃 누락, 리소스 미정리 등 잠재적 hang/leak이 없는가
- 에러 핸들링이 적절한가 (조용히 삼키는 catch가 안전한 맥락인가)
- 보안 관련 이슈가 없는가 (입력 검증, 인증/인가 등)

### 구조

- 중복 코드가 있는가 (같은 로직이 여러 파일에 복사되어 있지 않은가)
- 관심사 분리가 적절한가
- 캡슐화를 깨는 접근(Reflect, 내부 프로퍼티 직접 참조 등)이 없는가
- PR 컨벤션 기준으로 범위가 적절한가

### 일관성

- 기존 코드베이스의 네이밍, 패턴, 구조와 일관적인가
- 같은 개념에 다른 이름을 쓰고 있지 않은가

## 4) 리뷰 완료 기준

| 상태 | 조건 |
|------|------|
| **Approve** | 머지 차단 이슈 없음. nit/제안만 있는 경우 |
| **Comment** | 의견이나 질문이 있지만 차단하지 않음 |
| **Request Changes** | `[must]` 또는 `[bug]` 코멘트가 있어 수정 후 재확인 필요 |

## 5) 안티패턴

- ❌ 변경 목적과 무관한 코드까지 전부 지적하기
- ❌ "이상 없습니다" 한 줄로 끝내기 (최소한 어떤 관점에서 확인했는지 남긴다)
- ❌ 대안 없이 "이건 아닌 것 같아요"만 남기기
- ❌ 모든 코멘트를 `[must]`로 남기기 (심각도 구분이 사라진다)
- ❌ 코멘트를 남기지 않고 Request Changes만 걸기
