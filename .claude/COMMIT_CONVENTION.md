# Commit Convention

Conventional Commits 형식을 따른다.

## 금지 조항: 에이전트 이름/서명 표기 금지

- 커밋 메시지 제목, 본문, 푸터에 에이전트 이름이나 도구 서명을 적지 않는다
- 예: `Made with Cursor`, `Generated by Claude`, `Co-Authored-By: Claude` 금지
- 커밋 메시지는 변경 내용과 의도만 기록한다

## 형식

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

## Type

| type       | 용도                              |
| ---------- | --------------------------------- |
| `feat`     | 새 기능 추가                      |
| `fix`      | 버그 수정                         |
| `refactor` | 리팩토링 (기능 변경 없음)         |
| `chore`    | 빌드, 설정, 패키지 등 잡일        |
| `docs`     | 문서 변경                         |
| `style`    | 코드 스타일 (포매팅, 세미콜론 등) |
| `test`     | 테스트 추가/수정                  |
| `perf`     | 성능 개선                         |

## Scope

변경 대상을 괄호 안에 표기한다. 패키지명 또는 컴포넌트/모듈 단위.

예시:

- `feat(perf): RegionLoadProfiler 유틸리티 추가`
- `fix(ruler): canvas 최대 폭 제한`
- `refactor(timeline): 드롭 핸들러 분리`

## 원칙: 커밋은 항상 나눈다

**여러 변경을 한 커밋에 합치지 않는다.** 기본 작업 흐름은 “스테이징을 목적별로 나누고, 커밋을 여러 번 찍는 것”이다.

- **권장이 아니라 규칙**이다. 리뷰·되돌리기·`git bisect`·책임 추적을 위해 변경 단위는 커밋 경계와 일치해야 한다.
- **큰 PR일수록** 커밋 개수가 많아지는 것이 정상이다. “한 번에 커밋하고 squash”로 목적이 다른 변경을 묶지 않는다 (팀에서 머지 시 squash만 허용하는 정책이 있어도, **로컬 히스토리는 분리해 둔다**).
- **에이전트/자동화**로 커밋할 때도 동일하다. 한 번의 `git commit`에 서로 다른 목적의 파일을 넣지 않는다.
- **예외**는 정말 긴급하고 사후 정리가 확정된 경우 등 팀이 명시한 경우뿐이다. 기본은 항상 분리.

## 커밋 분리 기준

**하나의 커밋 = 하나의 변경 목적**이다. 아래 기준을 만족하도록 **항상** 나눈다.

1. **새 유틸리티/모듈 추가** — 신규 파일은 단독 커밋
2. **기존 코드에 연결** — import + 호출부는 파일당 별도 커밋
3. **버그 픽스** — 수정 단위별 커밋 (원인이 다르면 분리)
4. **리팩토링** — 기능 변경과 섞지 않는다
5. **같은 파일, 다른 목적** — patch 단위로 나눠서 커밋

### 기본 원칙: "처음 생각보다 더 잘게 쪼갠다"

- 커밋이 크다고 느껴지면 **반드시 더 분리**한다
- 문서(`docs`) / 설정(`chore`) / 기능(`feat`) / 버그픽스(`fix`)는 한 커밋에 섞지 않는다
- "이 커밋만 되돌려도 안전한가?"에 **예**라고 답할 수 있어야 한다
- PR 설명이 길어지는 커밋은 분리 대상이다

### 분리 체크리스트 (커밋 전)

아래 중 하나라도 해당하면 커밋을 더 쪼갠다.

1. 파일 수가 많고 목적이 2개 이상이다
2. 신규 파일 추가와 기존 파일 연결이 함께 들어있다
3. lint/config 변경과 기능 코드가 같이 들어있다
4. 문서 변경과 코드 변경이 같이 들어있다
5. 타입/모델 변경과 UI 변경이 같이 들어있다

### 권장 커밋 크기

- 권장: **작은 단위 커밋** (리뷰어가 5분 내 이해 가능)
- 지양: "대규모 스캐폴딩 1커밋", "전체 구조 변경 1커밋"
- 목표: 기능 구현 시 최소 2-4개 커밋 (기반 추가 → 연결 → 검증/문서)

### 예시

```
feat(perf): RegionLoadProfiler 유틸리티 추가          ← 1. 신규 파일
feat(timeline): RegionLoadProfiler 계측 연결          ← 2. 연결
feat(waveform): RegionLoadProfiler 계측 연결          ← 2. 연결 (파일별 분리)
fix(ruler): canvas 최대 폭 제한 및 viewport-aware 렌더링  ← 3. 버그 픽스
```

```
docs(rebuild): 타임라인 MVP 체크리스트 문서 추가      ← 문서만
chore(lint): 레이어 경계 ESLint 규칙 추가             ← 설정만
feat(editor): command/store/logic 스캐폴딩 추가       ← 기반 코드
feat(app): EditorProvider 연결                          ← 진입점 연결
```

### 안티패턴

- ❌ 신규 유틸 + 연결 코드를 한 커밋에 몰아넣기
- ❌ 버그 픽스하면서 리팩토링도 같이 하기
- ❌ "여러 수정" 같은 모호한 커밋 메시지

## 메시지 규칙

### Description (첫 줄)

- **한글로 작성** (type/scope는 영어 유지)
- 마침표 없음
- 한 줄로 간결하게 (70자 이내 권장)

### Body (선택)

- description 다음에 빈 줄 하나 띄우고 작성
- 변경의 동기나 맥락을 설명 (what보다 why)
- 여러 문단 가능

### Footer (선택)

- body 다음에 빈 줄 하나 띄우고 작성
- `Refs: #123` — 관련 이슈 참조
- `Reviewed-by: Name` — 리뷰어 표기

### Breaking Change

- footer에 `BREAKING CHANGE: 설명` 작성
- 또는 type 뒤에 `!` 붙이기: `feat(api)!: description`
- SemVer MAJOR 버전 범프에 해당

### 예시

```
fix: 요청 경합 방지

요청 ID를 도입하고 최신 요청만 응답을 수락하도록 변경.
기존 타임아웃 기반 우회 로직 제거.

Refs: #123
```

```
feat(api)!: 상품 발송 시 고객에게 이메일 전송

BREAKING CHANGE: `notify` 메서드에 email 파라미터 필수
```
