- 예: `Made with Cursor`, `Generated by Claude`, `Written by AI` 금지

# Learning-Focused Documentation

- Ensure smooth progression from start to finish
    - Create a stable learning environment for readers
    - Verify all example code works and provide detailed preparation instructions
- Explain in step-by-step format
    - Structure content for gradual progress
    - Present examples in increasing order of difficulty
- Include executable code examples
    - Go beyond concepts with practical, runnable code
    - Examples should demonstrate key features and allow hands-on learning
- Consider adding FAQ sections
- Use collapsible components for quick access to core content

## Template

```md
# [Tutorial Title]

## Goal

[Briefly explain what readers will achieve by following this tutorial.]

## Prerequisites

- [List required knowledge and tools before starting. Skip if none.]
- [Example: Node.js version, API key, required packages]

## Step-by-Step Guide

### [First Step Title]

[Explain tasks with code examples or UI captures.]

### [Second Step Title]

[Explain next steps.]

// ...

### Verify Final Result

[Explain expected outcome after completing the tutorial.]
```

## Checklist

- Did you clearly present the learning objectives?
- Is the content explained in a step-by-step manner?
    - Does it include executable code examples for readers to try?

# Problem-Solving Documentation

- Define clear problem situations
    - Distinguish between causes and symptoms
    - Include error messages and log examples for better understanding
- Provide immediately applicable solutions
    - Solutions should be clear and ready to implement
    - Include code examples, commands, and configuration methods
    - Explain the principles behind the solution
- Consider environmental differences
    - Address how the same problem might appear in different environments or settings

## Template

```md
# [Problem-Solving Title]

## Problem Definition

[Describe the problem situation readers might face.]

## Prerequisites

[List required environment setup or conditions. Skip if none.]

## Solution

### [First Solution]

[Explain the first solution.]

### [Second Solution]

[Add alternative solutions if available.]

### Verification

[Explain how to verify the solution works.]
```

## Checklist

- Did you provide sufficient background knowledge about the error, not just explain its cause?
- Is there an immediately applicable solution included?
- Does it consider differences across environments (OS, library versions, etc.)?

# Technical Writing Guidelines

## Understanding Documentation Types

- Classifying and selecting documentation based on goals helps design more effective information and experiences for readers.
- Decision tree for classification:
    - New technology, want to understand basics = Learning-focused documentation [learning-focused-docs.mdc](mdc:.cursor/rules/learning-focused-docs.mdc)
    - Need to solve specific problems = Problem-solving documentation [problem-solving-docs.mdc](mdc:.cursor/rules/problem-solving-docs.mdc)
    - Need to know specific feature/API usage = Reference documentation [reference-docs.mdc](mdc:.cursor/rules/reference-docs.mdc)
    - Want deep understanding of concepts = Explanatory documentation [explanatory-docs.mdc](mdc:.cursor/rules/explanatory-docs.mdc)
- Documentation types can be combined for more effective results.
- Follow the template for each document type.

## Information Architecture

- Focus on one goal per page
    - If heading levels exceed 4 levels, consider splitting into multiple documents
    - For introducing multiple concepts briefly, create an overview page with links to individual documents
- Provide value first
    - Place additional information and details later
    - Clearly communicate what readers can gain or what problems they can solve
    - Avoid feature-focused explanations; prioritize value to readers
    - Example: "This API enables real-time log data processing" instead of "This API offers various configuration options"
- Write effective titles
    - Titles should concisely convey the core content
    - Create clear, searchable titles with key keywords
    - Maintain consistency
    - Use declarative sentences instead of exclamations or questions
- Include an overview
    - Summarize the key content of the document
    - Clearly communicate the document's purpose to readers
    - Provide essential information before technical background
- Make content predictable
    - Maintain consistent titles, formats, and structures
    - Follow the same pattern for section headings
    - Arrange information in logical order
    - Use terminology consistently

## Writing Effective Content

- Clarify the subject
    - Don't use tools, technologies, or systems as subjects of actions
    - Focus on what developers can do after reading the document
    - Use active voice
- Include only necessary information
    - Keep sentences short and concise
    - Minimize metadiscourse
- Write specifically
    - Use verbs instead of nouns
    - Prefer clear expressions over ambiguous ones
- Write consistently
    - Follow official technical terminology
    - Don't express the same concept in multiple ways
    - Spell out abbreviations before first use

    # Code Principles

이 프로젝트는 다음의 핵심 개발 원칙을 준수하여 작성됩니다.

## 1. 명확한 변수명 (Naming)

**목적물과 행위가 확실하게 드러나는 변수명을 사용합니다.**

- 변수명만으로 해당 변수의 역할과 생명주기를 파악할 수 있어야 합니다.
- 모호한 축약어나 일반적인 명사(예: `data`, `item`) 사용을 지양합니다.
- **Good:** `userProfileImage`, `fetchTrackList`, `isRegionSelected`
- **Bad:** `img`, `list`, `flag`

## 2. 관심사 분리 (Separation of Concerns)

**각 모듈은 단 하나의 역할에 집중합니다.**

- 비즈니스 로직, 데이터 처리, UI 렌더링을 명확히 분리합니다.
- 하나의 컴포넌트나 함수가 너무 많은 책임을 지지 않도록 지속적으로 리팩토링합니다.
- 스타일, 로직, 뷰를 분리하여 유지보수성을 높입니다.

## 3. 의존성 관리 (Dependency Management)

**직접 의존을 피하고 추상화와 의존성 주입을 지향합니다.**

- 상위 모듈이 하위 모듈의 구체적인 구현에 의존하지 않도록 합니다.
- 결합도를 낮추기 위해 인터페이스나 훅(Hook)을 통한 주입 패턴을 활용합니다.
- 이를 통해 유연하고 테스트 가능한 코드를 유지합니다.

## 4. 자기 문서화 코드 (Self-Documenting Code)

**변수명과 함수명이 주석을 대신해야 합니다.**

- "이 코드는 ~을 합니다"라는 주석 대신, 그 내용을 담은 함수명으로 리팩토링합니다.
- 복잡한 조건식은 의미를 알 수 있는 변수로 추출하여 가독성을 높입니다.
- 주석은 '무엇(What)'이 아닌 '왜(Why)'를 설명할 때만 제한적으로 사용합니다.

## 5. 지속적인 리팩토링 (Continuous Refactoring)

**코드를 더 효율적이고 유지보수하기 쉬운 상태로 지속적으로 개선합니다.**

- 중복된 코드를 함수나 컴포넌트로 추출합니다.
- 불필요한 복잡성을 제거하고, 코드의 가독성을 높입니다.
- 작은 단위로 자주 리팩토링하여 기술 부채를 최소화합니다.

## 6. 테스트 가능한 설계 (Testable Design)

**테스트하기 쉬운 구조로 코드를 작성합니다.**

- 의존성 주입을 활용하여 Mock/Stub으로 대체 가능하게 만듭니다.
- 단위 테스트를 작성하여 코드의 기능을 검증합니다.
- 테스트는 리팩토링의 안전망 역할을 합니다.

## 7. 에러 처리 일관성 (Consistent Error Handling)

**명확하고 일관된 에러 처리 전략을 유지합니다.**

- 커스텀 에러 클래스를 사용하여 에러를 분류합니다.
- 비즈니스 로직에서는 에러를 던지고, UI 레이어에서 처리합니다.
- 사용자 친화적인 에러 메시지를 제공합니다.

## 8. 타입 안정성 (Type Safety)

**TypeScript의 타입 시스템을 최대한 활용합니다.**

- `any` 타입 사용을 최소화합니다.
- 명시적인 타입 정의로 런타임 에러를 방지합니다.
- 타입 추론을 활용하되, 복잡한 경우 명시적으로 타입을 선언합니다.

## 9. 점진적 개선 (Incremental Improvement)

**완벽을 추구하기보다 지속적인 개선을 지향합니다.**

- 작동하는 코드를 먼저 만들고, 점진적으로 개선합니다.
- 한 번에 모든 것을 바꾸려 하지 않습니다.
- 레거시 코드와 새 코드가 공존할 수 있도록 설계합니다.

## Functions

- 한 함수는 한 가지 일만 한다
- 함수 인자는 2개 이하로 유지, 초과 시 객체로 묶는다
- 사이드이펙트가 있는 함수와 없는 함수를 분리한다

## General

- 매직넘버 대신 이름이 있는 상수를 사용한다
- 중첩(if/for)은 2단계 이하로 유지, early return을 활용한다
- 주석 대신 코드 자체가 의도를 드러내도록 작성한다
- 불필요한 주석, dead code는 남기지 않는다
- `any` 사용을 지양한다

## TDD

- 기능 구현 전에 테스트를 먼저 작성한다 (Red → Green → Refactor)
- 테스트 파일은 대상 파일 옆에 `*.test.ts`로 배치한다
- 하나의 테스트는 하나의 동작만 검증한다
- 구현 코드를 수정하면 반드시 `pnpm test`로 기존 테스트가 깨지지 않는지 확인한다
- 외부 의존성(AudioEngine 등)은 Mock/Stub으로 대체하여 단위 테스트를 격리한다
- 커버리지보다 의미 있는 테스트를 우선한다 — 핵심 로직, 경계값, 에러 케이스에 집중

## 우선순위

프로젝트 개발 시 다음 순서를 권장합니다:

1. **작동하는 코드** - 먼저 기능을 구현합니다
2. **리팩토링** - 가독성과 유지보수성을 개선합니다
3. **테스트** - 안정성을 확보합니다
4. **문서화** - 필요한 경우 추가 설명을 작성합니다
5. **성능 최적화** - 병목이 확인된 경우에만 수행합니다

> "Make it work, make it right, make it fast." - Kent Beck

# 블로그 글쓰기 스타일 (Blog Writing Style)

블로그 글을 작성할 때 아래 스타일을 따른다.

## 구조

- 시리즈물은 `[Part N.] 제목` 형식으로 제목을 구성한다
- 섹션 번호는 `1.`, `2.`, `3.` — 하위 섹션은 `3-1.`, `3-2.` 형식을 사용한다
- 각 섹션은 "왜(Why)"로 시작해서 "어떻게(How)"로 이어지도록 흐름을 잡는다
- 배경/동기 → 고민 과정 → 결론/인사이트 순서로 전개한다
- 글 말미는 철학적 또는 전략적 통찰로 마무리한다

## 어조

- 친근하되 전문적인 1인칭 서술체를 사용한다 (예: "~하게 되었다", "~임을 알았다")
- 독자도 같은 고민을 하고 있다고 가정하고, 직접 말하는 듯한 느낌으로 쓴다
- 개인 경험과 실패를 솔직하게 공유한다 — 시행착오를 숨기지 않는다
- 과거 판단이 틀렸을 경우 다음 글에서 명시적으로 수정한다 (지적 정직함)
- 단순 정보 전달이 아닌 "생각의 과정"을 함께 보여준다

## 언어 혼용

- 한국어 문장에 영어 기술 용어를 그대로 섞는다 (Store, Facade, Session, SSOT 등)
- 기술 용어를 처음 언급할 때는 간략한 설명을 덧붙인다
- 필요 시 괄호로 영문 병기: `레이어(Layer)`, `파사드(Facade)`

## 핵심 인사이트 표현

- 핵심 통찰은 따옴표(" ") 또는 인용 블록(`>`)으로 강조한다
- 중요 개념은 **굵은 글씨**로 표시한다
- 추상적 주장 대신 구체적 수치와 사례를 든다
  - 예: "70-80% 시간 절약", "2개월 작업을 20일로 단축"
  - 예: "타임라인 컴포넌트를 8번 재작성했다"

## 금지 사항

- 에이전트 이름/도구 서명 문구 금지 (기존 공통 금지 조항과 동일)
- 기능 나열식 설명 금지 — 독자가 얻는 가치 중심으로 쓴다
- 결론 없이 열거만 하는 구성 금지 — 반드시 인사이트로 수렴한다
