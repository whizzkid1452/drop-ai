# 2026 프론트엔드 면접 플레이북

## Goal

2026년 기준으로 자주 나오는 프론트엔드 면접 질문을 우선순위대로 정리하고, 각 질문에 대해 모범답안/감점 포인트/안전 표현/암기 장치를 한 번에 학습한다.

## Prerequisites

- 프론트엔드 기본 지식(React, JavaScript, 브라우저 동작, HTTP)
- 30초~1분 답변 연습 환경(녹음 앱 또는 스터디)

## Step-by-Step Guide

### Step 1. 사용법 먼저 익히기

- 우선순위 1~10은 반드시 암기한다.
- 각 항목은 `정의/원리/실무/트레이드오프 4문장` + `감점 표현` + `안전 표현` 순으로 외운다.
- 마지막의 `30초 답변 공식`으로 실전 말하기를 반복한다.

### Step 2. 전체를 외우는 암기 주문

- `렌-URL-코-인-보-메-렌-저-생-최`
- 의미: 렌더링, URL, CORS, 인증, 보안(HTTPS), 메서드, 렌더링 전략(CSR/SSR), 저장소, 생명주기, 최적화

### Step 2-1. 병맛 암기 스토리 (한 번에 외우기)

면접날, 나는 **렌**더링 중독 개발자로 등장한다.  
지각해서 택시 앱에 **URL**을 찍었더니 기사님이 "프로토콜 뭐냐"부터 물어본다.

회사 로비에 도착하니 **코**끼리 경비원이 코로 출처 스캔을 하면서  
"허용 출처 아니면 문 못 열어줌"이라고 한다.

겨우 통과하려는데 인사팀이 "**인**증 방식 뭐 씀?"이라고 묻는다.  
나는 "상황 따라 Session도 쓰고 JWT도 씁니다"라고 말했더니 고개를 끄덕인다.

그다음 문은 **보**안문이라 HTTPS 아니면 자동으로 튕기고,  
옆 면접관이 "평문 들고 오면 바로 탈락"이라고 속삭인다.

면접실 들어가서 물 달라길래 HTTP **메**서드로 주문했는데  
GET으로 물을 '조회'만 하고 못 가져와서 분위기가 얼어붙는다.

다음 질문은 "**렌**더링 전략 뭐 쓸래?"라서  
나는 "랜딩은 SSR, 대시보드는 CSR"이라고 외치며 생존한다.

마지막으로 "데이터 어디 둘 건데?"라길래 **저**장소 3형제(local/session/cookie)를 펼치고,  
"민감 정보는 위협 모델 보고 결정"이라고 말하자 면접관 눈빛이 부드러워진다.

근데 갑자기 긴장해서 내 멘탈 **생**명주기가  
Mount(자신감) -> Update(식은땀) -> Unmount(도망)로 흘러간다.

끝판왕 질문은 성능 이슈.  
나는 "**최**적화는 측정 -> 원인 -> 국소 적용입니다!"라고 외치고 합격한다.

#### 5초 복기 주문

- "렌더하다 URL 타고 코끼리 통과, 인증하고 보안문 열고 메서드 외치고 렌더링 고르고 저장하고 생명주기 버티고 최적화로 끝."

## 우선순위 TOP 20

### 1) 브라우저 렌더링 과정 (최빈출)

#### 모범답안

1. 정의 1문장: 브라우저 렌더링은 HTML/CSS를 화면의 픽셀로 바꾸는 전체 처리 과정입니다.  
2. 핵심 원리 1문장: DOM/CSSOM 생성 후 Render Tree를 만들고 Layout, Paint, Composite 순서로 화면을 완성합니다.  
3. 실무 적용 1문장: 성능 이슈가 있으면 DevTools에서 Layout/Paint 비용을 측정하고 `transform`, `opacity` 중심으로 애니메이션을 설계합니다.  
4. 트레이드오프 1문장: 시각 품질을 높일수록 렌더링 비용이 커질 수 있어 품질과 프레임 안정성을 함께 맞춰야 합니다.

#### 감점 포인트

- "Virtual DOM 쓰면 무조건 빠릅니다."
- "Paint만 빠르면 렌더링 문제는 끝납니다."

#### 안전 표현

- "병목은 상황별로 다르므로 Performance 패널로 Layout/Paint/Composite를 확인합니다."
- "애니메이션은 가능한 Composite 단계에서 처리되도록 설계합니다."

#### 암기 장치

- 두문자: `파-스-레-페-합` (파싱-스타일-레이아웃-페인트-합성)
- 병맛 한 줄: 파스타집에서 주문 파악 -> 소스 고르기 -> 접시 레이아웃 -> 페인트처럼 색 입히고 -> 합체 플래터로 완성.

### 2) 주소창에 URL 입력 후 동작

#### 모범답안

1. 정의 1문장: URL 입력 후 동작은 브라우저가 네트워크를 통해 리소스를 받아 화면에 표시하는 절차입니다.  
2. 핵심 원리 1문장: DNS 조회, 연결 수립(TCP+TLS 또는 QUIC), HTTP 요청/응답, 파싱/렌더링 순서로 진행됩니다.  
3. 실무 적용 1문장: 느린 페이지는 DNS 시간, TTFB, 캐시 적중률, CDN 경로를 분리해 병목을 확인합니다.  
4. 트레이드오프 1문장: 보안과 안정성을 강화할수록 핸드셰이크 비용이 늘 수 있어 캐시와 커넥션 재사용 전략이 중요합니다.

#### 감점 포인트

- "항상 TCP로만 연결합니다."
- "DNS 조회 순서는 언제나 완전히 고정입니다."

#### 안전 표현

- "HTTP/2, HTTP/3와 캐시 상태에 따라 실제 경로는 달라질 수 있습니다."
- "핵심은 DNS/연결/요청응답/렌더링 흐름입니다."

#### 암기 장치

- 두문자: `DNS-연결-요청-렌더`
- 병맛 한 줄: 배달 주소 찾고(DNS) 기사 연결하고 주문 넣고 음식 오면 입에서 렌더링된다.

### 3) CORS와 대응 방법

#### 모범답안

1. 정의 1문장: CORS는 브라우저가 교차 출처 요청의 허용 여부를 판단하는 보안 정책입니다.  
2. 핵심 원리 1문장: 단순 요청 조건을 벗어나면 preflight(OPTIONS)로 허용 출처, 메서드, 헤더를 먼저 검증합니다.  
3. 실무 적용 1문장: 서버에서 `Access-Control-Allow-*` 헤더를 정확히 설정하고 쿠키 요청은 `credentials`와 함께 일치시켜 운영합니다.  
4. 트레이드오프 1문장: 보안을 엄격히 할수록 개발 편의성이 떨어질 수 있어 환경별 허용 정책을 분리해야 합니다.

#### 감점 포인트

- "CORS는 서버끼리 통신할 때도 막습니다."
- "막히면 일단 `*`로 다 열면 됩니다."

#### 안전 표현

- "CORS는 브라우저 보안 모델에 의한 제약입니다."
- "운영 환경에서는 허용 출처를 명시적으로 제한합니다."

#### 암기 장치

- 두문자: `출처검사-사전검사-허용헤더`
- 병맛 한 줄: 클럽 입구 코끼리 경비원이 출처검사하고 수상하면 가방검사(preflight) 후 팔찌(허용헤더) 주고 입장시킨다.

### 4) Session vs JWT

#### 모범답안

1. 정의 1문장: Session과 JWT는 인증 상태를 유지하는 대표적인 두 방식입니다.  
2. 핵심 원리 1문장: Session은 서버 저장소 기반이고 JWT는 토큰 서명 검증 기반으로 상태를 판단합니다.  
3. 실무 적용 1문장: 단일 서비스는 Session, 분산 환경은 JWT 또는 혼합 전략으로 선택하고 만료/재발급 정책을 함께 설계합니다.  
4. 트레이드오프 1문장: Session은 관리가 쉬운 대신 서버 상태 비용이 있고 JWT는 확장성이 좋은 대신 폐기 통제가 어렵습니다.

#### 감점 포인트

- "세션은 매번 전체 사용자 데이터를 보냅니다."
- "JWT는 서버 부하가 거의 없습니다."

#### 안전 표현

- "보안/운영 요구사항에 따라 혼합 전략(짧은 만료, 재발급, 폐기 정책)을 사용합니다."

#### 암기 장치

- 두문자: `세션=보관함 / JWT=증명서`
- 병맛 한 줄: 락커키(세션)는 헬스장 기록 확인형, 주민증(JWT)은 카드 확인형인데 잃어버리면 둘 다 멘붕이다.

### 5) HTTPS와 HTTP 차이

#### 모범답안

1. 정의 1문장: HTTPS는 HTTP 통신에 TLS를 적용해 안전하게 데이터를 주고받는 방식입니다.  
2. 핵심 원리 1문장: TLS는 암호화, 무결성, 서버 인증을 제공해 중간자 공격 위험을 줄입니다.  
3. 실무 적용 1문장: 운영에서는 인증서 갱신 자동화, HTTP→HTTPS 리다이렉션, HSTS 설정을 기본으로 관리합니다.  
4. 트레이드오프 1문장: 보안 강화를 위해 초기 연결 비용이 늘 수 있어 캐시와 프로토콜 최적화를 같이 가져가야 합니다.

#### 감점 포인트

- "HTTPS는 암호화만 하면 끝입니다."
- "보안은 백엔드만 신경 쓰면 됩니다."

#### 안전 표현

- "HTTPS 핵심은 인증서 신뢰 체인과 무결성 보장입니다."
- "프론트도 쿠키 속성과 mixed content 차단을 함께 다룹니다."

#### 암기 장치

- 두문자: `암-무-인` (암호화-무결성-인증)
- 병맛 한 줄: 비밀편지에 자물쇠 걸고(암호화), 봉인 스티커 붙이고(무결성), 발신자 도장 찍어야(인증) 열어준다.

### 6) GET/POST, PUT/PATCH 차이

#### 모범답안

1. 정의 1문장: HTTP 메서드는 리소스에 대해 어떤 의도를 가진 요청인지 표현하는 규약입니다.  
2. 핵심 원리 1문장: GET은 조회, POST는 생성/처리, PUT은 전체 교체, PATCH는 부분 변경 의미로 주로 사용됩니다.  
3. 실무 적용 1문장: API 문서와 서버 구현이 일치하도록 메서드 의미를 계약하고 클라이언트도 그 규칙을 따릅니다.  
4. 트레이드오프 1문장: REST 의미를 엄격히 지킬수록 설계는 명확해지지만 기존 API와의 호환 조정 비용이 생길 수 있습니다.

#### 감점 포인트

- "PUT/PATCH 의미는 절대 규칙입니다."

#### 안전 표현

- "HTTP 의미론을 따르되 팀 API 계약을 함께 확인합니다."

#### 암기 장치

- 두문자: `G조회 P생성 U전체 P부분`
- 병맛 한 줄: 식당에서 GET으로 메뉴만 보고, POST로 주문하고, PUT은 세트 통교체, PATCH는 반찬만 살짝 바꾼다.

### 7) CSR vs SSR (필요 시 SSG)

#### 모범답안

1. 정의 1문장: CSR과 SSR은 화면을 어디서 생성하느냐를 결정하는 렌더링 전략입니다.  
2. 핵심 원리 1문장: CSR은 브라우저 렌더링 중심, SSR은 서버에서 초기 HTML 생성 후 하이드레이션하는 방식입니다.  
3. 실무 적용 1문장: 대시보드형 페이지는 CSR, 검색 유입 랜딩 페이지는 SSR/SSG로 나누는 하이브리드 구성이 일반적입니다.  
4. 트레이드오프 1문장: CSR은 초기 로딩 부담이, SSR은 서버 비용과 구현 복잡도가 커질 수 있어 목표 지표 기준으로 선택해야 합니다.

#### 감점 포인트

- "SSR은 항상 빠릅니다."
- "CSR은 SEO가 불가능합니다."

#### 안전 표현

- "요구사항(SEO, 개인화, 캐시 전략)에 따라 렌더링 방식을 분리합니다."

#### 암기 장치

- 두문자: `CSR=현장조리 / SSR=완성배달`
- 병맛 한 줄: 집에서 직접 요리하면 CSR, 완성 음식 배달오면 SSR이라 상황 따라 섞어 먹는 게 정답이다.

### 8) localStorage / sessionStorage / cookie

#### 모범답안

1. 정의 1문장: localStorage, sessionStorage, cookie는 브라우저에서 데이터를 저장하는 대표 수단입니다.  
2. 핵심 원리 1문장: localStorage는 장기 저장, sessionStorage는 탭 단위 저장, cookie는 요청 자동 포함과 속성 제어가 핵심입니다.  
3. 실무 적용 1문장: 인증 관련 데이터는 위협 모델을 기준으로 저장 위치와 `HttpOnly`, `Secure`, `SameSite` 정책을 함께 설계합니다.  
4. 트레이드오프 1문장: 접근성과 구현 편의성을 높일수록 보안 노출 면적이 커질 수 있어 보안 정책과 함께 사용해야 합니다.

#### 감점 포인트

- "토큰은 로컬 스토리지에 항상 저장하면 됩니다."
- "쿠키는 구식이라 안 써도 됩니다."

#### 안전 표현

- "인증 정보는 위협 모델 기준으로 저장소와 방어 전략을 함께 결정합니다."
- "쿠키는 HttpOnly/Secure/SameSite를 기본으로 검토합니다."

#### 암기 장치

- 두문자: `로-세-쿠` (로컬-세션-쿠키)
- 병맛 한 줄: 로컬 냉장고는 오래 보관, 세션 컵은 오늘만 사용, 쿠키통은 손님 오면 자동으로 꺼내진다.

### 9) React 라이프사이클 / useEffect

#### 모범답안

1. 정의 1문장: 컴포넌트 라이프사이클은 마운트, 업데이트, 언마운트의 변화 흐름입니다.  
2. 핵심 원리 1문장: 함수형 컴포넌트에서는 `useEffect`와 cleanup으로 외부 시스템 동기화를 처리합니다.  
3. 실무 적용 1문장: API 호출, 이벤트 구독, 타이머는 effect에서 시작하고 언마운트 시 반드시 정리합니다.  
4. 트레이드오프 1문장: effect를 과도하게 쓰면 의존성 관리가 복잡해지므로 렌더 계산과 부수효과를 분리해야 합니다.

#### 감점 포인트

- "`useEffect`는 상태 계산용으로도 쓰면 됩니다."
- "의존성 배열은 비워두면 안전합니다."

#### 안전 표현

- "`useEffect`는 부수효과 전용으로 사용하고 의존성을 명시적으로 관리합니다."

#### 암기 장치

- 두문자: `마-업-언` (마운트-업데이트-언마운트)
