# Drop-AI 재구축 1편: 기능 목록보다 먼저 해야 할 것

기능 목록을 먼저 쓰면 안 멈춰진다.  
"이것도 있으면 좋겠다"가 반복되고, 20개 기능이 금방 쌓인다.  
무엇을 만들지보다 **왜 만드는지**를 먼저 고정해야 그 목록을 자를 수 있다.

## 문제: 무엇이 문제였는가

처음에 기능 목록을 먼저 작성했다.  
재생, 트랙, 리전, 루프, BPM, 내보내기, 타임라인, 자동화 커브, 플러그인…

문제는 모든 기능이 "있으면 좋을 것 같다"는 느낌이라는 점이다.  
기준 없이 나열하면 무엇을 먼저 만들어야 할지 판단이 안 된다.

증상은 기능이 너무 많다는 것이었다.  
원인은 "완성"이 무엇인지 정의하지 않았다는 것이었다.

```mermaid
flowchart LR
  A["기능 아이디어 20개"] --> B{우선순위?}
  B --> C["모두 MVP처럼 느껴짐"]
  C --> D["어디서 멈춰야 하는지 불명확"]
```

## 선택: 어떤 방식으로 범위를 잠글 것인가

세 가지 방식을 고려했다.

| 방식 | 접근 | 단점 | 판단 |
| --- | --- | --- | --- |
| 기능 목록 우선 | 가능한 기능을 모두 나열하고 자른다 | 자르는 기준이 없어서 범위가 다시 늘어난다 | 제외 |
| 기술 스펙 우선 | 구현 가능한 것부터 정의한다 | 사용자 가치와 연결이 끊겨 있다 | 제외 |
| 사용자 시나리오 우선 | 먼저 시나리오를 3개 고정하고 그것을 만족하는 기능만 MVP로 본다 | 초기에 합의 비용이 든다 | 채택 |

판단 기준은 하나였다.  
**"한 주 안에 시연 가능한가?"**  
시나리오 기준으로 잘라야 이 질문에 답할 수 있었다.

## 해결: 어떻게 범위를 고정했는가

### 1) 문제를 한 문장으로 먼저 쓴다

기능 목록 이전에 이 한 문장을 먼저 합의한다.

> "오디오 클립을 트랙 단위로 배치하고 재생/편집할 수 있는 최소 DAW를 웹에서 구현한다."

이 문장이 이후 기능 요청이 올 때마다 판단 기준이 된다.  
새 기능이 이 문장을 직접 개선하지 않으면 후순위다.

### 2) 기능 목록 대신 시나리오 3개를 먼저 쓴다

기능이 아니라 사용자의 행동 흐름을 먼저 고정한다.

1. 트랙을 만들고 오디오 파일을 올려서 재생한다.
2. 루프, BPM, 볼륨을 조절하면서 반복 청취한다.
3. 편집한 세션을 WAV 파일로 내보낸다.

이 세 가지를 만족하면 "작동하는 최소 제품"이다.  
이 시나리오를 기준으로 비로소 기능을 자를 수 있다.

### 3) 시나리오 기준으로 MVP와 후순위를 자른다

| 구분 | 기능 | 해당 시나리오 |
| --- | --- | --- |
| MVP | 재생/정지/일시정지, seek | 1, 2 |
| MVP | BPM, 루프, 마스터 볼륨 | 2 |
| MVP | 트랙 추가/삭제, 볼륨/팬/mute/solo | 1, 2 |
| MVP | 리전 추가/이동/삭제/분할/리사이즈 | 1 |
| MVP | 세션 상태 확인, WAV 내보내기 | 3 |
| 후순위 | 고급 타임라인 편집 UX | 없음 |
| 후순위 | 자동화 커브, 플러그인 체인 | 없음 |
| 후순위 | 협업 기능, 클라우드 저장 | 없음 |

후순위 기능을 버린 이유는 성능이나 복잡도 때문이 아니었다.  
단순히 세 개의 시나리오를 만족하는 데 필요하지 않았기 때문이다.

### 4) 끝 조건을 명시한다

구현이 끝났는지 판단하는 기준을 미리 고정한다.

- 재생 제어: 버튼 입력 후 체감상 즉시 반응
- 트랙/리전 편집: 주요 명령이 오류 없이 세션 상태에 반영
- 내보내기: 빈 세션 방지, 유효한 WAV 파일 생성
- 품질 게이트: `pnpm test`, `pnpm lint`, `pnpm typecheck`, `pnpm build` 통과

이 기준 없이 구현에 들어가면 "언제 끝났는지"를 나중에 합의해야 한다.

### 5) 도메인 용어를 코드와 동일하게 고정한다

초기에 용어를 통일하지 않으면 "트랙이 클립을 가지는가, 클립이 트랙에 붙는가"처럼 회의마다 다시 정의하게 된다.

| 용어 | 의미 |
| --- | --- |
| Session | 현재 프로젝트의 전체 상태 |
| Track | 오디오/리전을 담는 믹싱 단위 |
| Region | 타임라인에 배치되는 오디오 조각 |
| Transport | 재생/정지/루프/BPM 같은 전역 제어 |

이 용어는 이후 코드 타입 이름과 동일하게 사용한다.  
`TrackState`, `RegionState`, `SessionData`처럼.

## 결과: 실제로 어떻게 달라졌는가

범위를 고정하기 전과 후의 차이는 아래와 같다.

| 항목 | 고정 전 | 고정 후 |
| --- | --- | --- |
| 기능 요청 처리 | 매번 새로 판단 | 시나리오 기준으로 즉시 판단 |
| 구현 완료 기준 | 불명확 | 끝 조건이 수치로 명시됨 |
| 용어 혼선 | 회의마다 재정의 | 코드와 동일한 용어 사용 |
| 범위 이탈 | 기능이 계속 추가됨 | 시나리오 외 기능은 후순위로 분리 |

한계도 있다.  
시나리오 3개가 실제 사용자 요구를 충분히 대표하는지는 이 단계에서 검증할 수 없다.  
이 문서는 내부 합의 기준이고, 실제 검증은 시연 이후다.

## FAQ

### Q1. 시나리오가 바뀌면 MVP 기준도 다 바뀌는가?

바뀐 시나리오를 만족하지 못하는 기능은 후순위로 내리고, 새로 필요한 기능만 추가한다.  
시나리오가 기준이기 때문에 기능 목록이 바뀌어도 판단 로직은 동일하다.

### Q2. 혼자 만드는 프로젝트에서도 이 과정이 필요한가?

혼자일수록 "지금 이게 맞는 방향인가"를 자주 물어보게 된다.  
시나리오와 끝 조건을 고정해두면 그 질문에 즉시 답할 수 있다.

### Q3. UI를 먼저 만들면 더 빠르지 않나?

짧게 보면 빠르다.  
하지만 상태 모델 없이 UI를 만들면 기능이 늘면서 리팩토링 비용이 누적된다.  
범위 고정에 드는 시간보다 재작업 비용이 훨씬 크다.
